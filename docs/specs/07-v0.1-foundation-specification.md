**Initial Build and Minimum Viable Product Specification**

*Windows-first • Local-first • Beginner-friendly • Extensible by design*

| **Release objective ---** A non-technical user moves from no local-AI environment to a verified local response in one guided desktop flow---without manually installing a runtime, selecting quantization settings, or opening a terminal. |
|----|

# 1. Purpose and Product Position {#purpose-and-product-position}

GixGiz is a desktop platform that abstracts the setup and management of local language models. Version 0.1 is the first production-oriented foundation: it validates the user experience while establishing stable interfaces for the wider platform. Later releases may add secure system tools, coding agents, AI Packs, additional runtimes, cloud escalation, enterprise administration, and a developer SDK; none of those should require the v0.1 core to be discarded.

The MVP proves one central claim: users should interact with goals and clear recommendations, while GixGiz handles hardware detection, planning, approved installation, verification, runtime communication, and recovery behind the scenes. It is therefore more than a chat frontend, but deliberately less than the complete future platform.

# 2. Users, Platform and Primary Scenario {#users-platform-and-primary-scenario}

| **Area** | **Definition** |
|----|----|
| **Primary user** | A student, educator, professional, small-business user, or beginner who wants private local AI but does not understand runtimes, model formats, quantization, CUDA, or CLI setup. |
| **Secondary user** | A developer who wants a dependable local AI environment and a future common endpoint for IDEs, tools, and agents. |
| **Initial platform** | Windows 11 on x64. OS-specific behavior is isolated behind platform providers so Linux and macOS can be added later. |
| **Primary scenario** | Install GixGiz, scan the machine, review one suitable recommendation, approve runtime/model setup, and begin a streaming local conversation. |

# 3. Required v0.1 Outcomes {#required-v0.1-outcomes}

A single onboarding journey from first launch to successful local inference.

A truthful machine capability report with rationale, confidence, warnings, storage estimate, and a conservative alternative.

Detection and reuse of an existing Ollama installation, or explicit user-approved installation when absent.

Resumable model preparation, runtime health verification, test inference, streaming chat, and local history.

A runtime abstraction that contains all Ollama-specific behavior and permits later adapters without UI changes.

Operational logging, cancellation, restart recovery, and clear removal/cleanup behavior.

# 4. Scope Boundary {#scope-boundary}

Included: onboarding, hardware scan, capability analysis, model catalogue/recommendation, Ollama lifecycle, model download, readiness test, chat, settings, persistence, diagnostics, recovery, and packaging. Deferred: cloud/hybrid routing, multiple runtimes, autonomous filesystem or terminal agents, AI Packs marketplace, SDK, enterprise console, voice, images, RAG knowledge bases, mobile clients, and account sync.

# 5. End-to-End User Flow {#end-to-end-user-flow}

| **Stage** | **Expected behavior** |
|----|----|
| **1. First launch** | Explain local processing and permissions; choose model-storage location; run prerequisite checks. |
| **2. Machine scan** | Collect CPU, RAM, GPU, reliable VRAM, disk, OS/architecture, and accelerator indicators into a normalized profile. |
| **3. Capability report** | Show workload tier, limitations, estimated resources, one recommendation, and a lower-demand fallback. |
| **4. Plan review** | List runtime/model sources, storage impact, elevation needs, and ordered steps. No system change occurs before approval. |
| **5. Runtime preparation** | Detect/version-check Ollama, start it if stopped, or run a logged, resumable installation and verify health. |
| **6. Model preparation** | Precheck free space, pull the selected model with progress/cancel/retry, then verify it is available. |
| **7. Readiness and chat** | Run a small test inference, record health/latency, open streaming chat, and preserve conversation history. |
| **8. Recovery** | Identify the failed stage, retain completed work, allow safe retry, and expose sanitized diagnostics. |

# 6. Functional Requirements {#functional-requirements}

FR-01 --- Produce a versioned MachineProfile; unavailable facts are explicitly unknown, never guessed.

FR-02 --- Generate an explainable CapabilityReport using deterministic, testable rules and an updateable model catalogue.

FR-03 --- Distinguish Ollama states: absent, installed/stopped, ready, incompatible, and degraded.

FR-04 --- Execute setup as persisted steps with preflight checks, approval gates, progress events, cancellation, retry, verification, and cleanup.

FR-05 --- Track models, expected/actual size, runtime identity, readiness, storage location, and removal state.

FR-06 --- Support streaming chat, stop generation, new/rename/delete conversation, persistent history, active-model details, and structured errors.

FR-07 --- Provide settings for storage, launch behavior, diagnostics, optional telemetry, and asset removal.

FR-08 --- Expose a typed local API/IPC boundary so future clients can reuse GixGiz without connecting directly to Ollama.

FR-09 --- Maintain an append-only audit trail for installation, removal, runtime lifecycle, and other system-changing operations.

# 7. UX and Control Principles {#ux-and-control-principles}

| **Intent over infrastructure ---** Default copy describes outcomes such as "Recommended for general use and coding." Model size, quantization, context, and runtime details remain available in an advanced view. |
|----|

Ask before installing software, elevating privileges, changing configuration, or removing data.

Always show the active stage, what is happening, expected storage/time where known, and a safe cancel route.

Base "Ready" on verified runtime health and successful inference---not merely an installer exit code.

Preserve progress across restarts and explain failures in plain language while retaining technical diagnostics.

Offer one recommended path by default, but show alternatives and their trade-offs.

# 8. Happy-Path Completion Definition {#happy-path-completion-definition}

The setup wizard is complete only when the runtime is healthy, the recommended model is listed by the runtime, a test prompt returns a valid streamed response, and the workspace can create and reload a local conversation. Any earlier state is "setup in progress" or "attention required," not success.

# 9. High-Level Architecture {#high-level-architecture}

| **Layer** | **Responsibility** |
|----|----|
| **Flutter Desktop UI** | Onboarding, capability report, setup progress, chat, settings, accessibility. |
| **Typed Local Boundary** | Commands, queries, progress streams, cancellation, and versioned error contracts. |
| **GixGiz Core** | Workflow coordination, configuration, persisted state, audit events, and policy. |
| **Platform Services** | Hardware Scanner, Capability Engine, Installer, Download Manager, Model Manager, Diagnostics. |
| **Runtime Abstraction** | RuntimeAdapter contract for detect/install/start/health/list/pull/chat. |
| **Ollama Adapter + Host** | Ollama API/process implementation over Windows, storage, network, CPU/GPU resources. |

# 10. Core Module Specifications {#core-module-specifications}

| **Module** | **Boundary and responsibility** |
|----|----|
| **Desktop Application** | Presentation only. It displays core state and emits typed user intentions; it never runs shell commands or contains recommendation/runtime logic. |
| **Hardware Scanner** | Uses replaceable Windows providers; normalizes units; records source and uncertainty; never infers accelerator support from a product name alone. |
| **Capability Engine** | Combines MachineProfile and catalogue constraints to return model/fallback, resource estimates, confidence, rationale, and warnings. |
| **Workflow Coordinator** | Orders setup steps, persists state, resumes interruptions, prevents conflicting operations, and maps internal failures to user-facing states. |
| **Runtime Manager** | Owns lifecycle and selects an adapter. Runtime-specific endpoints, commands, and data formats are forbidden outside adapters. |
| **Ollama Adapter** | Implements detection, version/health, start/stop, model listing/pull, chat streaming, and error translation. |
| **Installer/Download Engine** | Performs source and disk prechecks, integrity validation where available, approval, progress, retry, cancellation, verification, and safe cleanup. |
| **Model & Persistence Services** | SQLite stores schema-versioned settings, workflow state, catalogue metadata, model records, conversations/messages, and audit events. |
| **Diagnostics Service** | Builds privacy-conscious logs/support bundles; prompts and conversation content are excluded by default. |

# 11. Versioned Data Contracts {#versioned-data-contracts}

MachineProfile contains OS/architecture, CPU, logical cores, total/available RAM, GPUs, reliable dedicated VRAM, accelerator indicators, storage volumes, scan time, provider source, and unknown fields. CapabilityReport contains tier, selected model/fallback, estimated storage/RAM/VRAM, confidence, rationale, warnings, and catalogue version. RuntimeStatus contains adapter ID, install/version/process/health state, capabilities, and last error. InstallationPlan contains ordered steps, sources, approvals, resource estimates, completion state, and cleanup actions. ChatRequest/ChatEvent contains conversation/model IDs, messages, generation options, streamed text, cancellation, latency/usage metadata, and structured failures.

# 12. Technology Baseline {#technology-baseline}

Flutter provides the Windows desktop interface; Rust provides domain logic and system services; SQLite stores local state; Tokio runs asynchronous work; the local boundary uses Axum HTTP or a direct Flutter--Rust bridge selected after a small benchmark/prototype; GitHub Actions validates formatting, linting, tests, dependency audit, and Windows builds. Ollama is the only v0.1 runtime, but no shared domain type should be named after it.

# 13. Repository Boundary {#repository-boundary}

Recommended monorepo areas: apps/desktop; crates/gixgiz-core, hardware-scanner, capability-engine, runtime-api, runtime-ollama, installer-engine, persistence, diagnostics; docs/; tests/. The root AGENTS.md defines architecture, security, testing, and Codex working rules. Public interfaces are documented and changes require an architecture decision record when they alter module ownership or contracts.

# 14. Security, Privacy and Reliability {#security-privacy-and-reliability}

| **Control** | **Requirement** |
|----|----|
| **Least privilege** | Run normally without administrator rights. Request elevation only for the exact approved step and never retain it silently. |
| **Trusted acquisition** | Use approved runtime/model sources; validate signature/checksum or other integrity metadata where available; fail closed on mismatches. |
| **Local privacy** | History, settings, and diagnostics remain local. Telemetry is absent or explicit opt-in, minimal, documented, and excludes prompts/files. |
| **Local API safety** | Bind to loopback only; use an installation-scoped authentication mechanism where appropriate; do not expose services to the LAN by default. |
| **Safe recovery** | Persist step state, make retries idempotent, prevent duplicate installation/pulls, track partial assets, and never delete unrelated user software/data. |
| **Auditability and truth** | Record system-changing actions and sanitized outcomes. Display success only after health and test-inference verification. |

# 15. Non-Functional Targets {#non-functional-targets}

Usability --- a first-time user completes the supported happy path without external documentation or terminal commands.

Responsiveness --- scans, downloads, installation, and inference never block the UI; progress is event-driven.

Reliability --- restart-safe workflow, idempotent retry, cancellation, timeouts, and clear degraded states.

Maintainability --- strict ownership, typed errors, versioned schemas, small modules, dependency justification, and architecture tests.

Testability --- unit tests for rules/state machines, adapter mocks, installation integration tests, and packaged Windows smoke tests.

Accessibility --- keyboard navigation, scalable text, screen-reader labels, contrast, and non-color-only progress/error communication.

Compatibility --- publish minimum Windows/hardware requirements and gracefully reject unsupported environments.

# 16. Alpha 0.1 Acceptance Criteria {#alpha-0.1-acceptance-criteria}

AC-01 --- A clean supported Windows machine completes setup and produces a local streamed response entirely through the GUI.

AC-02 --- An existing healthy Ollama installation is detected and reused; stopped/degraded/incompatible installations are distinguished.

AC-03 --- Low disk, unsupported architecture, failed start, interrupted pull, and failed inference produce specific recoverable states.

AC-04 --- Recommendations explain selection and remain within configured conservative resource thresholds.

AC-05 --- Long operations can be cancelled; restart resumes valid work without state corruption or duplicate actions.

AC-06 --- History persists locally, can be deleted, and diagnostics exclude conversation content by default.

AC-07 --- Flutter and shared modules contain no direct Ollama endpoint or command usage.

AC-08 --- Formatting, linting, unit/integration/security checks, and the Windows build all pass in CI.

# 17. Delivery Sequence and Principal Risks {#delivery-sequence-and-principal-risks}

| **Area** | **Plan** |
|----|----|
| **M0 --- Foundation** | Repository, AGENTS.md, architecture decisions, Flutter--Rust boundary, CI, logging, configuration, and core health call. |
| **M1 --- Know the machine** | Windows scanner, normalized profile, capability rules, catalogue, recommendation UI. |
| **M2 --- Prepare runtime** | Ollama detection/lifecycle, installer plan, approvals, integrity checks, progress, recovery. |
| **M3 --- Prepare model** | Storage preflight, model pull, progress/cancel/retry, verification, registry. |
| **M4 --- Prove value** | Streaming chat/history, readiness test, diagnostics, accessibility, packaging, alpha release. |
| **Key risks** | Unreliable cross-vendor hardware facts, upstream installer/API changes, large downloads, antivirus/elevation behavior, and inaccurate estimates. Mitigate with provider/adaptor isolation, version checks, resumability, conservative rules, catalogue updates, and real post-install benchmarking. |

| **Definition of success ---** A supported non-technical Windows user can install GixGiz and receive a verified local-model response in under ten minutes without a terminal or manual runtime configuration, while the delivered core remains suitable for the complete future GixGiz platform. |
|----|
